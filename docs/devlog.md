**수정 (`dashboard/notifier.py`, 이동준 작성 코드를 수정)**

| 항목 | 수정 전 | 수정 후 |
|---|---|---|
| 대상 조회 쿼리 | `logs` 전체 스캔, 223만 행에서 약 375ms | status 인덱스 사용, 약 7~20ms |
| 전송 방식 | 블록당 메시지 1건 | 쌓인 이상을 메시지 1건에 묶음 (1건이면 상세, 여러 건이면 요약) |
| E2E 지연 (아래 측정 조건 참고) | p95 4.6초, 2초 이내 50% (시뮬레이션) | p95 1.49초, 2초 이내 100% |
| 메시지 | 평문, UTC 시각 | 긴급/경고 표시, 운영자용 문구, KST, 원본 로그, 대시보드 링크 |
| 실패 처리 | `pending` 이 영구히 남음, 재전송 수단 없음 | 시작 시 `failed` 로 표시, `--retry-failed` 로 직접 재전송 |

**추가**
- 대시보드: Slack 링크(`?block=블록ID`)로 열면 SQLite 모드에서 그 블록으로 걸러진 상태로 시작한다.
- `start.sh`: `.env` 에 Webhook 주소가 있으면 알림 프로그램도 함께 실행한다. `NO_SLACK=1` 로 끌 수 있다.
- 로그 내용이 Slack 문법(`<!channel>` 등)으로 해석되지 않도록 처리했다.
- 테스트 37개 → 44개.

**측정 조건과 한계**
- 수정 전 수치는 2만 줄 재생 기록에 전송 간격을 적용한 시뮬레이션이다.
- 수정 후 수치는 test 로그 4만 줄을 재생하며 알림 작업자를 함께 돌려 잰 값이다 (이상 블록 35개, 메시지 22건). 두 수치는 조건이 다르다.
- 전송은 응답 0.2초의 가짜 함수로 대체했고 HTTP 서버 없이 같은 프로세스에서 실행했다. **실제 Slack 전송과 실제 서버 환경의 E2E 는 아직 측정하지 않았다.**
