## 3. 단계별 진행 방법

### ② 실행

```bash
./start.sh demo
```

- 터미널에 `준비 완료: {"status":"ok","model_ready":true,"model":"autoencoder"...}` 와 `Slack 알림: 켜짐` 이 나오는지 확인
- 브라우저가 대시보드를 연다 → 사이드바 데이터 소스가 **`SQLite`** 로 선택되어 있는지 확인 (`start.sh` 는 SQLite 로 연다. '데모 데이터' 면 가짜 데이터이므로 바꾼다)
- 참고: `./start.sh`(빠른 시연, 앞 2만 줄)도 되지만 세션 종료 판정은 보여 줄 수 없고, `LIMIT=5000` 처럼 적게 주면 이상이 없어 알림이 가지 않는다 (첫 이상 약 13,000줄째). **시연은 demo 모드를 쓴다**

### ③ 실시간 처리

- 터미널: 5초마다 `저장 N행 | 정상 | 이상` 숫자가 늘어난다
- 대시보드: 자동 갱신(5초)으로 '관측 세션' 숫자가 늘고, 점수 추이 그래프가 1초 단위로 그려진다

### ④ 이상 탐지 → Slack (재생 시작 후 약 5초부터)

- 터미널 '이상' 숫자가 0 에서 늘기 시작하면 곧 Slack 메시지가 온다
- 🔴 **긴급 카드** (그 유형이 처음 나왔을 때 즉시): 유형 이름(예: 블록 쓰기 중 네트워크·입출력 오류), 쉬운 설명, 블록, 관련 노드(추정), 블록 흐름(`수신 시작 → … → ⚠️ 쓰기 입출력 오류`), **권장 조치**, 원본 로그
- 🟠 **경고 요약** (20초마다): "이상 블록 9개 — 유형별 개수 + 예시"
- 멘트: "이상은 모두 탐지·기록하지만, 블록마다 알림을 보내면 사람이 알림을 무시하게 됩니다(알림 피로). 그래서 새로운 종류는 즉시, 반복은 요약으로 보냅니다. 블록 하나하나는 대시보드에서 봅니다"

### ⑤ 세션 종료 판정·정확도 (재생 끝, 약 30초)

- 재생이 끝나면 자동으로 세션 종료 판정을 하고 터미널에 채점 결과가 나온다

```
[demo] 시연 샘플 세션 1,000개 (실제 이상 28개) 채점
   실시간 판정만        : 이상 23개 탐지 · 오탐 1 · 놓침 5 → F1 0.885
   + 세션 종료 판정     : 이상 27개 탐지 · 오탐 1 · 놓침 1 → F1 0.964  (종료 판정으로만 잡은 이상 4개)
```

- 멘트: "중간에 끊긴 세션은 로그가 더 이상 안 오는 것 자체가 이상이라, 세션이 끝난 뒤 종료 토큰(EOS)을 붙여 한 번 더 판정합니다. 이 4개는 실시간으로는 못 잡고 종료 판정으로만 잡았습니다" (전체 test 기준 0.880 → 0.977 과 같은 경향)
- Slack 에는 끊긴 세션이 처음 나오면 긴급 카드(`작업이 중간에 끊긴 블록`), 나머지는 다음 20초 요약에 포함되어 온다
- 대시보드 '세션 상세' 탭: 세션마다 "정상 종료 / 끊긴 세션 → 이상" 표시

### ⑥ 원인 확인

1. Slack 메시지의 **▶ 대시보드에서 보기** 클릭 → 그 블록만 걸러진 대시보드가 열린다
2. '실시간 모니터링' 탭 → '최근 추론 윈도우' 표의 **판정 근거** 칸: `실제: … → 모델 예상: …`
3. '세션 상세' 탭 → 세션 선택 → 그 블록의 전체 이벤트 흐름
4. '알림 이력' 탭 → 보낸 알림이 `sent` 로 기록됨 ("같은 블록은 한 번만 알립니다")

### ⑦ 처음 보는 로그 직접 입력

1. 브라우저 새 탭: http://127.0.0.1:8000/docs → `POST /logs` → **Try it out**
2. 아래 내용을 붙여 넣고 **Execute**

```json
{"raw_log": "081109 203615 148 WARN dfs.DataNode: totally new disk failure on blk_999000111 sector 42"}
```

3. 응답에 `"status": "anomaly"`, `"reason": "unknown_event"`, `"anomaly_score": 1.0`
4. 1~2초 안에 Slack 에 `🔴 긴급 · 새 유형 첫 발생` — `처음 보는 형식의 로그` 카드 (시연 샘플에는 이 유형이 없어서 첫 입력은 항상 긴급). 블록 번호를 바꿔 한 번 더 보내면 이번에는 같은 유형의 반복이라 20초 요약으로 간다

비교용 정상 로그 (점수가 0 에 가깝게 나온다):

```json
{"raw_log": "081109 203518 143 INFO dfs.DataNode$DataXceiver: Receiving block blk_777000222 src: /10.250.19.102:54106 dest: /10.250.19.102:50010"}
```

같은 블록 번호로 여러 번 보내면 두 번째부터는 알림이 가지 않는다 (블록당 1회). 다시 시연하려면 블록 번호 숫자를 바꾼다.

### ⑧ 모델 성능

- '모델 평가' 탭: 방법별 Precision / Recall / F1 표와 막대그래프
- 멘트: "test 세션 11만 5천 개를 마지막에 한 번만 평가한 결과입니다. 세션 종료 토큰(EOS)을 넣어 0.884 → 0.977 이 됐습니다"

### ⑩ 마무리

- 터미널에서 `Ctrl+C` → 서버·대시보드·알림이 함께 꺼진다

## 4. 문제가 생기면

| 증상 | 원인 | 대처 |
|---|---|---|
| `가상환경이 없습니다` | `make setup` 안 함 | `make setup` |
| `재생할 데이터가 없습니다` | `make data` 안 함 | 시간 없으면 `./start.sh serve` 로 켜고 ⑥ 직접 입력만 시연 |
| `Address already in use` | 이전 실행이 남아 있음 | 터미널 닫았다 다시 열고 `pkill -f uvicorn; pkill -f streamlit` 후 재실행 |
| `Slack 알림: 꺼짐` | `.env` 없음 | 알림 없이 진행, 대시보드 '알림 이력' 대신 판정 근거 위주로 설명 |
| Slack 메시지가 안 옴 | 인터넷·Webhook 문제 | `artifacts/run_logs/notifier.log` 확인. 시간 없으면 백업 영상 |
| 대시보드에 'Demo Autoencoder' | 데이터 소스가 '데모 데이터' | 사이드바에서 `SQLite` 선택 |
| 대시보드가 비어 있음 | 재생 전이거나 SQLite 경로 다름 | 경로 `artifacts/api/logguard.sqlite` 확인, '지금 새로고침' |
| 전부 안 됨 | — | 백업 영상 재생 + 발표 자료의 실측 수치로 설명 |

## 5. 질문 대비 (자세한 답: 중간발표 예상 질문 정리)

- "세션 끝은 어떻게 아나요?" → 마지막 로그 뒤 150만 줄 동안 소식이 없거나 재생이 끝나면 EOS 를 붙여 한 번 더 판정 (실시간만 0.880 → 종료 판정 포함 0.977)
- "실시간이라면서 왜 단일 워커인가요?" → 같은 블록의 이벤트 순서 보장. Slack 전송은 별도 프로세스라 느려도 수신에 영향 없음
- "이상마다 알림이 오면 너무 많지 않나요?" → 등급 정책: 새 유형 첫 발생·이상 급증만 즉시, 나머지는 20초 요약 (전체 재생 기준 수천 건 → 유형 수 + 요약 몇 건). E2E 2초 목표는 즉시 보내는 긴급 알림 기준
- "실제 운영에 쓸 수 있나요?" → 인증·배포·다른 로그 종류 적용은 범위 밖 (향후 과제). 구조는 그대로 확장 가능
