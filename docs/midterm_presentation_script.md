## ① 슬라이드별 대본

### 1. 표지 (15초)
> 안녕하십니까, 7조 옥상민, 이동준, 안명근입니다.
> 저희 프로젝트는 **DeepLog-Guard**, AI 기반 실시간 서버 로그 이상 탐지 및 알림 시스템입니다.
> 지금까지 구현한 결과를 보고드리겠습니다.

### 2. 목차 (10초)
> 구현 내용, 정량적 성과, 화면(UI) 설명, 향후 개선할 내용, 참고 자료 순서로 말씀드리겠습니다.

### 3. 문제 정의와 핵심 성과 (50초)
> 2022년 판교 데이터센터 화재처럼 대형 장애에는 전조 증상이 있지만, 규칙 기반 모니터링은 "에러라는 단어가 있는가" 같은 단편적인 기준만 보기 때문에 미리 잡아내기 어렵습니다.
> 저희는 로그를 **작업 단위(블록)의 흐름**으로 보고, 평소 흐름과 다른지를 딥러닝으로 판단하는 파이프라인을 만들었습니다.
>
> 핵심 성과는 세 가지입니다.
> 첫째, 탐지 성능 지표인 **F1이 0.977**로 목표 0.85를 넘었고, 규칙 기반(0.573)보다 **40.4%p** 높습니다.
> *(슬라이드 제목은 "탐지 정확도"지만 F1은 정확도(accuracy)가 아님. "탐지 성능"이라고 말할 것. Q3-1 참고)*
> 둘째, 로그 한 줄을 해석하고 판정하는 데 **0.10ms**(p95)가 걸립니다. 목표는 1초 이내였습니다.
> 셋째, 모델 처리 경로 기준으로 단일 스레드에서 **초당 약 1만 700줄**을 처리해, 목표 초당 500줄의 약 21배입니다.
> *(0.10ms와 1만 700줄은 HTTP·DB를 뺀 "파싱 + 모델 판정" 기준입니다. 질문이 나오면 ②-1 참고)*

### 4. 시스템 구조 (40초)
> 전체 구조는 다섯 단계입니다.
> ① 로그 재생 모듈이 HDFS 원본 로그를 실제 서버처럼 한 줄씩 보냅니다.
> ② FastAPI 서버가 받아서
> ③ Drain 파서로 로그를 템플릿 번호로 바꾸고, Autoencoder가 이상 점수를 계산합니다.
> ④ 결과는 SQLite 한 파일에 저장되고,
> ⑤ 같은 DB를 **Slack 알림 작업자**와 **Streamlit 대시보드**가 각각 따로 읽습니다.
> 서버, 알림, 대시보드를 분리해서 하나가 느려지거나 멈춰도 로그 수신은 계속됩니다.

### 5. Drain 로그 구조화 (45초)
> 로그는 문장이라 그대로는 모델에 넣을 수 없습니다. Drain 알고리즘으로 블록 번호, IP, 숫자처럼 바뀌는 값을 지우고 "PacketResponder <NUM> for block <BLK> terminating" 같은 **템플릿**으로 묶어 번호를 붙입니다.
> 그런데 기본 유사도 기준 0.5에서는 정상인 "terminating"과 이상 신호인 "Interrupted"가 같은 템플릿으로 합쳐지는 문제를 발견했습니다. 그렇게 되면 모델 입장에서는 이상 신호가 사라집니다.
> 기준을 **0.85**로 올려 문제를 없앴고, Loghub 공식 정답과 블록 57만 5천여 개 전체를 비교해 **100% 일치**하는 52개 템플릿을 얻었습니다.

### 6. 모델 비교 (45초)
> 모델은 두 가지 방식을 비교했습니다.
> **DeepLog**는 LSTM으로 직전 이벤트들을 보고 "다음 이벤트"를 예측합니다. 실제 다음 이벤트가 예측 상위 K개 안에 없으면 이상입니다.
> **Autoencoder**는 이벤트 20개짜리 창(윈도우)을 작게 압축했다가 다시 복원합니다. 정상만 학습했기 때문에 처음 보는 패턴은 잘 복원하지 못하고, 그 **복원 오차가 임계치를 넘으면** 이상으로 판정합니다.
> 두 모델 모두 정상 세션만으로 학습했고, 임계치는 검증 데이터의 정상 세션 점수 분포로 정했습니다.

### 7. EOS 토큰 (50초)
> 가장 큰 성능 향상은 모델 구조가 아니라 **데이터를 이해한 데서** 나왔습니다.
> 데이터 분석(EDA)을 해 보니 이상 세션의 약 37%는 정상 세션의 최소 길이(13개)보다 짧았습니다. 그중 상당수는 에러 로그 없이 **작업이 중간에 그냥 끊긴** 세션이었습니다. 다음 이벤트만 보는 모델은 "멈췄다"는 사실 자체를 볼 수 없습니다.
> 그래서 세션 끝에 **EOS(End-of-Sequence) 토큰**을 붙여, 모델이 "여기서 끝나도 정상인가"까지 배우게 했습니다.
> 그 결과 test F1이 DeepLog 0.821 → 0.926, Autoencoder 0.884 → 0.977로 올랐습니다.
> 알고리즘을 바꾸는 것보다 도메인 특성을 반영한 데이터 모델링이 더 효과적이었다는 점이 핵심입니다.

### 8. 최종 모델 선정 (40초)
> 네 가지 방법의 test 결과입니다. 규칙 기반은 정밀도는 높지만 재현율이 0.41에 그쳤습니다.
> Autoencoder + EOS가 정밀도 0.970, 재현율 0.984, **F1 0.977**로 가장 높았고, 시드 3개로 반복해도 평균 0.978, 편차 0.001로 안정적이었습니다.
> 속도도 한 줄 판정에 Autoencoder 약 0.09ms, DeepLog 약 0.53ms로 **약 5~6배 빨라**, 실시간 시스템에 맞는 Autoencoder를 최종 채택했습니다.
> 참고로 모든 설정은 검증 데이터로만 정했고, test는 마지막에 **한 번만** 평가했습니다.

### 9. 실시간 대시보드 (40초)
> 대시보드 화면입니다. 왼쪽에서 데이터 소스, 조회 기간, Block ID 검색을 고를 수 있고, 5초마다 자동으로 갱신됩니다.
> 위쪽에 관측 세션 수, 이상 세션 수와 비율, Slack 알림 성공 건수를 보여 주고,
> 아래 그래프는 이상 점수 추이입니다. 점수는 0~1로 맞춰 두어서 **0.5 기준선**을 넘으면 이상입니다.
> *(이 화면은 데모(합성) 데이터 화면입니다. 질문이 나오면 ②-3 참고)*

### 10. 판정 근거 (40초)
> 딥러닝은 왜 이상인지 설명하기 어렵다는 한계가 있어서, 판정마다 **근거**를 함께 저장했습니다.
> 예를 들어 "이 위치의 실제 이벤트는 '블록 삭제'인데, 모델은 '수신 완료'가 와야 한다고 봤다"처럼, 가장 복원이 안 된 이벤트와 모델이 기대한 이벤트를 보여 줍니다.
> 원본 로그 한 줄도 함께 보여 줘서, 운영자가 바로 원인을 찾을 수 있습니다.

### 11. 알림 시스템 (40초)
> Slack 알림 작업자는 서버와 분리된 별도 프로그램으로, 0.5초마다 DB를 확인합니다.
> 실시간 판정이나 세션 종료 판정에서 이상이 나오면 알림 대상이 되고, 같은 블록·모델 조합은 DB의 **유일 키**로 한 번만 알림을 보냅니다.
> 전송 결과는 성공(sent), 실패(failed)로 기록해 나중에 다시 보낼 수 있습니다.

### 12. 현재 한계 (30초)
> 중간 시점의 한계는 세 가지였습니다.
> 첫째, 로그 전송부터 Slack 도착까지의 **전체(E2E) 지연**을 아직 재지 못했습니다.
> 둘째, 알림 작업자가 중간에 꺼지면 보내던 알림의 상태가 남는 문제가 있었습니다.
> 셋째, Locust를 이용한 통합 부하 테스트를 아직 못 했습니다.

### 13. 향후 계획 (25초)

## ③ 예상 질문과 답

### 데이터·전처리
**Q1. 왜 HDFS 데이터셋인가? 실제 서비스 로그에도 쓸 수 있나?**
> HDFS_v1은 블록 57만 5천여 개마다 정상·이상 정답이 붙어 있는 대표 공개 데이터라 성능을 객관적으로 잴 수 있습니다. 구조는 "로그 → 템플릿 → 작업 단위 세션 → 순서 패턴 학습"이라, 세션을 묶을 ID(요청 ID, 트랜잭션 ID 등)가 있는 로그면 같은 방식으로 적용할 수 있습니다. 다만 새 로그에서는 Drain 템플릿과 모델을 다시 학습해야 합니다.

**Q2. 세션(블록) 단위로 나눈 이유는? 데이터 누수는?**
> 정답이 블록 단위로 주어지고, 한 블록의 생성·복제·삭제가 하나의 작업 흐름이기 때문입니다. 윈도우를 먼저 자르고 나누면 같은 블록 조각이 train과 test에 동시에 들어가 점수가 부풀려집니다. 그래서 **블록 단위로 먼저 6:2:2로 나누고**, 각 셋 안에서만 윈도우를 만들었습니다. train에는 정상 세션만 넣었습니다(이상 1만 102개는 제외).

**Q3. 클래스 불균형(이상 약 2.9%)은 어떻게 처리했나?**
> 정상만 학습하는 비지도(이상 탐지) 방식이라 불균형의 영향을 직접 받지 않습니다. 평가는 정확도(accuracy) 대신 이상 클래스 기준 정밀도·재현율·F1을 썼습니다. 정상이 97%라 전부 정상이라고만 해도 정확도는 97%가 나오기 때문입니다.

**Q3-1. 슬라이드에 "탐지 정확도 (F1)"라고 했는데, F1이 정확도인가?**
> 정확히는 아닙니다. 정확도(accuracy)는 전체 중 맞힌 비율이고, test에서 Autoencoder 정확도는 0.999입니다. 하지만 이상이 2.9%뿐이라 전부 정상이라고 해도 정확도가 97%가 나와서 의미가 없습니다. 그래서 **이상 클래스 기준 정밀도(0.970)와 재현율(0.984)의 조화평균인 F1(0.977)**을 주 지표로 썼습니다. 슬라이드의 "정확도"는 "탐지 성능"이라는 뜻으로 쓴 표현입니다.
> (test 혼동행렬: 이상을 맞힘 3,314 · 정상을 이상으로 봄 102 · 이상을 놓침 55 · 정상을 맞힘 111,544)

**Q4. Drain 유사도 0.85는 어떻게 정했나?**
> 여러 sim_th·depth 조합을 Loghub 공식 템플릿 29개(정답)와 비교해 그룹 정확도와 "서로 다른 이벤트가 합쳐진 줄 수"를 쟀습니다. 합쳐짐은 이상 신호를 지우기 때문에 가장 해롭다고 보고, 합쳐짐이 0이 되는 0.85를 골랐습니다. 일부 이벤트가 더 잘게 쪼개져 템플릿이 52개가 됐지만, 블록 단위로는 공식 이벤트 시퀀스와 100% 일치합니다.

**Q5. 학습 때 없던 새 로그가 들어오면?**
> 실시간 서버는 저장된 템플릿과 **매칭만** 하고 새 템플릿을 만들지 않습니다(학습·실시간 번호가 어긋나지 않게). 매칭이 안 되면 "모르는 이벤트(UNK)"로 보고 **즉시 이상** 처리합니다. 처음 보는 형식은 새 장애이거나 소프트웨어 변경일 가능성이 높기 때문입니다.

### 모델
**Q6. Autoencoder 구조와 입력은?**
> 이벤트 20개짜리 윈도우를 원-핫(22종류)으로 바꿔 440차원 벡터로 만들고, 440 → 64 → 32(잠재) → 64 → 440 MLP로 복원합니다. 손실은 위치별 교차 엔트로피 합(원래 이벤트를 복원할 확률의 −log)이고, 이 값이 재구성 오차입니다. 파라미터는 약 6만 1천 개, CPU 학습에 약 1분 걸립니다.

**Q7. 원-핫인데 왜 MSE가 아니라 교차 엔트로피인가?**
> 각 위치는 "22개 중 하나"인 분류 문제라서, 맞는 이벤트에 확률을 얼마나 줬는지 보는 교차 엔트로피가 더 자연스럽습니다. MSE는 틀린 이벤트가 어떤 것이든 비슷한 오차를 내서 구분력이 떨어집니다.

**Q8. 임계치는 어떻게 정했나? "동적 임계치"인가?**
> 검증 데이터 **정상 세션** 점수의 백분위수 후보(99.0~100, 0.05 간격) 중 검증 F1이 가장 높은 값을 골랐고, 99.9 백분위수인 6.78입니다. 실행 중에 바뀌는 값은 아니고, 학습 후 고정입니다. 슬라이드의 "동적"은 데이터 분포로 정했다는 뜻이고, 사람이 정한 고정값이 아니라는 의미입니다. 화면에는 점수를 s/(s+6.78)로 바꿔 기준선이 항상 0.5가 되게 했습니다.

**Q9. 윈도우 크기 20, 잠재 32는 왜?**
> 윈도우 10·15·20, 잠재 16·32 조합을 시드 3개로 학습해 **검증 F1 평균**으로 골랐습니다(5단계 튜닝, `results/tuning_autoencoder_summary.csv`). test는 쓰지 않았습니다.

**Q10. DeepLog가 논문에서는 좋은데 왜 졌나?**
> DeepLog도 EOS를 붙여 0.926까지 올렸지만, "상위 K개 안에 있냐"는 기준이 거칠어서 정상인데 드문 흐름을 이상으로 보는 오탐이 많았습니다(정밀도 0.898). Autoencoder는 윈도우 전체를 한 번에 보기 때문에 흐름 전체의 어색함을 더 잘 잡았고, 속도도 5~6배 빨랐습니다.

**Q11. 과적합은 아닌가? test를 여러 번 본 것 아닌가?**
> 모든 선택(Drain 설정, 윈도우, 임계치)은 검증 데이터로만 했고, test는 마지막 6단계에서 **한 번** 평가했습니다. 검증 F1 0.972, test 0.977로 거의 같아 과적합 징후가 없고, 시드 3개 편차도 0.001입니다.

**Q12. 실시간에서는 세션이 끝나기 전에 판정해야 하는데 EOS는 어떻게 쓰나?**
> 두 단계로 나눴습니다. 로그가 올 때마다 **방금 이벤트로 끝나는 윈도우**를 판정하는 실시간 판정과, 세션이 끝났다고 볼 때(재생 종료 또는 오래 소식 없음) **마지막에 EOS를 붙인 윈도우**를 판정하는 세션 종료 판정입니다. 실시간 판정만으로는 F1 약 0.88이고, 종료 판정까지 합치면 0.977이 됩니다. 끊긴 세션은 끊겼다는 사실을 알 때까지 기다려야 하므로 이 차이는 구조적으로 생깁니다.

**Q13. 세션이 끝났다는 건 어떻게 아나?**
> HDFS는 종료 로그가 따로 없어서, 그 블록의 마지막 로그 뒤로 **150만 줄 동안 소식이 없으면** 끝난 것으로 봅니다(정상 블록도 이벤트 사이가 최대 약 130만 줄 벌어져서 여유를 둠). 시연·평가에서는 재생이 끝난 뒤 한꺼번에 종료 판정합니다. 판정 뒤 새 로그가 오면 그 블록만 다시 판정해 갱신합니다.

### 시스템·성능
**Q14. 0.10ms와 실제 서비스 지연은 다르지 않나?**
> 맞습니다. 0.10ms는 모델 경로입니다. 실제로는 서버 안 처리(수신 → 판정 → 저장) p95 약 0.5ms이고, 로그 전송부터 Slack 도착까지 E2E는 실제 Slack 기준 최대 1.82초로 목표 2초 안입니다. E2E 대부분은 Slack 서버 응답과 Slack 전송 간격(초당 약 1건 제한) 시간입니다.

**Q15. 처리량 1만 700줄인데 서버는 왜 수백 건인가?**
> 1만 700줄은 모델만 잰 값이고, 서버는 HTTP 요청 처리와 SQLite 쓰기가 줄마다 들어갑니다. 또 블록별 순서를 지키려고 한 번에 한 요청만 처리합니다. Locust 50명 실측은 초당 약 480건, 실패 0입니다. 더 키우려면 여러 줄을 묶어 받는 배치 API나 블록별로 나눠 처리하는 구조가 필요합니다.

**Q16. 왜 단일 워커(직렬 처리)인가?**
> 같은 블록의 로그 순서가 섞이면 윈도우가 틀어져 판정이 달라집니다. 정확성을 우선해 직렬 처리했고, 판정 자체가 0.1ms 수준이라 병목은 아닙니다.

**Q17. 왜 SQLite인가? 동시에 읽고 쓰면 문제없나?**
> 팀 프로젝트 규모에서는 설치 없이 파일 하나로 되는 SQLite가 적합했습니다. WAL 모드를 켜서 서버가 쓰는 동안에도 대시보드·알림 작업자가 동시에 읽을 수 있고, 대시보드는 읽기 전용으로 엽니다. 규모가 커지면 PostgreSQL 같은 서버형 DB로 바꾸면 되고, 테이블 정의는 `schema.sql` 한 곳에 모아 두었습니다.

**Q18. 서버를 껐다 켜면 블록 이력은?**
> 블록별 최근 이벤트를 메모리가 아니라 **DB에서 매번 꺼내** 쓰기 때문에, 재시작해도 이력이 이어집니다. 서버 시작 시 윈도우 크기와 단어장(어휘)이 모델과 맞는지 검사해서, 안 맞으면 서버가 아예 켜지지 않게 했습니다(조용히 틀린 판정을 막기 위해).

### 알림·화면
**Q19. 알림이 너무 많이 오면?**
> 중간발표 이후 실제로 전체 로그 재생 때 알림이 86건 쏟아지는 문제가 있어, 등급 정책을 넣었습니다. **이번에 처음 나온 이상 유형**이나 **이상 급증**(평소 대비 3배 이상)만 즉시 긴급으로 보내고, 나머지는 20초마다 한 메시지로 요약합니다. 이상 템플릿 52개를 운영자가 알아보기 쉬운 유형 10개로 묶고, 유형마다 설명과 권장 조치를 붙였습니다.

**Q20. 알림 전송이 실패하면?**
> 실패하면 `failed`와 실패 이유를 기록하고 자동으로 계속 다시 보내지는 않습니다(장애 때 폭주 방지). 운영자가 `--retry-failed`로 다시 보낼 수 있습니다. 작업자가 보내는 도중 꺼지면 다음 시작 때 보내던 알림을 `failed`로 정리합니다.

**Q21. 오탐(false positive)은 얼마나 되나?**
> test 정상 세션 11만 1,646개 중 이상으로 잘못 본 것은 **102개(약 0.09%)**, 놓친 이상은 3,369개 중 55개입니다(정밀도 0.970, 재현율 0.984). 같은 조건에서 DeepLog는 오탐 365개였습니다. 오탐 상당수는 정상이지만 드문 흐름이라, 대시보드의 판정 근거(실제 이벤트 vs 모델 예상)로 운영자가 바로 확인할 수 있게 했습니다.

### 협업·기타
**Q22. 역할 분담은?**
> 옥상민: 데이터 전처리, 모델 학습·평가, 모델-서버 연결과 통합, 실행 스크립트. 이동준: Streamlit 대시보드, Slack 알림. 안명근: FastAPI 백엔드, 로그 재생, Locust 부하 시험. 세 사람이 같은 DB 규격(`schema.sql`)과 판정기 약속(인터페이스)을 먼저 정해 두고 병렬로 개발했습니다.

**Q23. 이 프로젝트의 한계는?**
> ① 공개 데이터셋 하나(HDFS)로만 검증했습니다. ② 끊긴 세션은 끝났다는 걸 알 때까지 기다려야 해서 실시간성에 한계가 있습니다. ③ 서버 처리량이 HTTP·SQLite에 묶여 있어 대규모 운영에는 배치 수신이나 DB 교체가 필요합니다. ④ 시스템이 바뀌면 템플릿과 모델을 다시 학습해야 합니다.
